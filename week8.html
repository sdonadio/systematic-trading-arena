WEEK 8

CI/CD, Testing & UI

A green run on your laptop proves nothing. This week your bot becomes trustworthy: tests that pin its behaviour, a pipeline that refuses to merge red code, an image that runs identically anywhere, and a dashboard that tells you it is alive.

  • Test at the right layer — and know which layer would have caught the bug that just cost you a session.
  • Wire a pipeline that runs pytest on every push and blocks the merge when it fails.
  • Read a live dashboard and say, in one glance, whether your bot is healthy or quietly broken.
What is it?

Production engineering: proving it works, everywhere, every time

Three habits, one goal — your bot behaves the same on your laptop, in CI, and on the live arena at 6:05pm with the class watching the leaderboard.

A test is an executable claim about your code. pytest discovers every function named test_*, runs it, and reports which claims still hold. That is all. The engineering judgement is not in writing asserts — it is in choosing which claim to make at which layer.

The pyramid is that judgement made visible. Many unit tests at the base, each pinning one function in milliseconds with no I/O. Fewer integration tests, wiring two or three components together with fakes instead of the network. A handful of end-to-end runs that drive the whole path — bot to exchange to fill to P&L — and catch the wiring bugs nothing else can see, slowly and a little flakily.

Push logic down. A bug caught by a unit test costs you seconds; the same bug caught end-to-end costs a minute of CI; the same bug caught live costs you a session, in public.

# tests/test_signal.py
from strategy import momentum_signal

def test_momentum_goes_long_on_uptrend():
    prices = [100, 101, 102, 103, 104]
    sig = momentum_signal(prices, lookback=3)
    assert sig.side == 'buy'
    assert sig.qty > 0

def test_momentum_flat_when_no_trend():
    assert momentum_signal([100, 100, 100], 3) is None
Name the test after the behaviour it pins. When it goes red six weeks from now, the name is the whole bug report. One behaviour per test, and @pytest.mark.parametrize for the variations.

How does it work?

A pipeline is a gate, and determinism is what makes it mean something

Continuous integration runs your suite on every push, on a clean machine that is not yours. Continuous delivery ships what passes. The merge stays blocked until the checks are green.

A GitHub Actions workflow is YAML in .github/workflows/. An event (on: [push]) triggers jobs; each job runs ordered steps on a fresh runner; a matrix fans the same job out across Python versions. Nothing in it is clever — and that is the point. The runner has no internet by design, no cached state, and none of your local environment. If your suite passes there, it passes anywhere.

on: [push, pull_request]        # trigger
jobs:
  test:                         # a job
    runs-on: ubuntu-latest      # the runner
    strategy:
      matrix:
        python: ['3.11', '3.12']  # fan out
    steps:                      # ordered
      - uses: actions/checkout@v4
      - run: make install
      - run: pytest -q

Reproducibility is the other half. Same code plus same dependencies plus same OS equals same behaviour, so pin exact versions (==, never >=), isolate in a venv, and freeze the whole environment in an image. Order the Docker layers stable-to-volatile so the pip install layer stays cached and only your code layer rebuilds.

# requirements.txt — pin exact versions
websockets==12.0
pydantic==2.7.1

# Dockerfile — freeze the environment
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .         # cached layer
RUN pip install -r requirements.txt
COPY . .                        # code layer
CMD ["python", "-m", "team.trader"]

Three sources of nondeterminism, three fixes. Randomness → seed it. The network → inject a fake or a recorded fixture; a CI runner has no internet anyway. The clock and IDs → pass them in, never call datetime.now() deep inside logic. A test that fails one run in twenty trains your team to ignore red, which defeats the entire point of having a suite.
Why does it matter in trading?

Live failures are public, and you cannot fix what you cannot see

A missing dependency, a hardcoded path, an untested edge case — any one of them crashes your bot mid-session while the dashboard shows the whole class your equity curve flatlining.

Shipping is not the end of the job. A running bot needs configuration you can change without a rebuild (ports, poll intervals — plain env vars), secrets that never enter git or the image (tokens injected at runtime), and observability: structured logs for what happened, metrics for what is happening now.

A dashboard is metrics made glanceable, and a trading dashboard has four non-negotiable panes. Positions — what do I own, and is it what I think I own. P&L — realized, unrealized, and the shape of the curve. Risk — how close am I to a limit, and what is my worst case right now. Connectivity — is the socket up, is the feed fresh, am I being throttled. Miss the fourth pane and you will confidently quote on a price that stopped updating four minutes ago.

The arena's own UI is exactly this: teacher/web_dashboard.py with MARKET (live books), FLOW (who trades with whom), STATS and SEASON (per-team analytics and standings). The deploy kit behind it — systemd units, Caddy for TLS, Docker for the environment — is how the hosted arena becomes reproducible from bare metal up.

Common mistakes

Five ways a tested bot still dies live

Each of these has cost a team a session. Each expands.

Tests that reach the network
A unit test that calls yfinance is not a unit test: it is slow, it changes every second, it fails on a plane, and it fails in CI where there is no internet by design. Worse, it passes locally, so you only discover it after you push.
Fix: inject a fake feed (class FakeFeed: def price(self, sym): return 185.0) or monkeypatch the call. Use tests/sim_session.py when you need a whole session.
Tolerating a flaky test
One test fails roughly one run in twenty, so the team learns to click "re-run". Now red means nothing, and the day a real regression lands nobody notices. A flaky test is worse than no test because it destroys the signal value of the whole suite.
Fix: treat a flake as a P1 bug. Seed the randomness, freeze the clock, remove the sleep-based timing, or delete the test. Never leave it amber.
Chasing the coverage number
Coverage measures which lines executed, not whether anything was asserted. You can reach 95% with tests that call every function and check nothing. Meanwhile the two branches that matter — the reject path and the reconnect path — are the untested ones, because they are the awkward ones.
Fix: read the report to find the gaps you did not know you had, and hold the source of truth (your signal and risk logic) to a high bar. Do not pad the number with trivial tests.
Unpinned dependencies and "works on my machine"
Your requirements.txt says pydantic>=2. Three weeks later the runner resolves a new minor version, a validator becomes stricter, and your bot cannot parse a message it has parsed all season. The code did not change; the environment did.
Fix: pin exact versions, commit the pin, and containerise. Order Docker layers stable-to-volatile so the dependency layer stays cached and the rebuild only touches your code.
A dashboard with no connectivity pane
Positions, P&L and risk all look perfect — because they are computed from a price that stopped updating four minutes ago. The socket is open, the process is alive, nothing has thrown, and you are quoting into a market that has moved on. Partial failure is the normal failure mode of a live system.
Fix: show feed age, socket state and reject rate next to the money, and alarm on staleness rather than on exceptions. Detect, do not assume.
Check yourself

Three questions

Instant feedback, no grading.

Question 1
Your on_tick returns a buy signal when it should return None. Which test layer should have caught it, and why that one?
B. Arrange a fake market and a portfolio, call on_tick, assert the Signal (or the None). Pushing this claim down to the base of the pyramid is what makes it cheap enough to run on every push.
Question 2
A test in your suite fails about one run in twenty, always with a different P&L. What is the correct response?
D. The other three all preserve the flake and destroy the signal. Seed the RNG, inject the clock, fake the feed. With the seed fixed, a red test fails the same way every time — which is the only reason a failure is debuggable.
Question 3
Mid-session, your dashboard shows a flat P&L, no rejects, positions unchanged, and a socket in OPEN. What is the first thing you check?
A. This is the classic partial failure: the transport is fine, the data is dead. Everything downstream still computes, confidently, from a frozen price. That is why the connectivity pane sits next to the money, and why staleness is an alarm rather than an exception.
