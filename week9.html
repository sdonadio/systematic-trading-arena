Part 1 · Testing

A test is an executable claim — put each claim at the cheapest layer that can see the bug

Why this part exists

Eight weeks of code now run every Friday in front of the class. Before you change any of it again, you need a way to know that the change did not break what worked. Tests are that way: executable claims you can run in seconds. Part 2 then shows how a team moves a tested change to production without touching a live session.

pytest finds every function named test_*, runs it and reports which claims still hold. The engineering is not in writing assert; it is in choosing which claim to make, at which layer, with which fake at the boundary.

The platform you have traded on all season is held together by its suite: 2,036 tests pass in 41.75 s with no network (measured on an M4 laptop; quote what yours prints), shared/orderbook.py is at 100% coverage because a wrong fill corrupts every P&L downstream, and every wire message is round-trip tested (dump to JSON, parse back, assert equal). The lab’s own test file runs 11 tests in 0.12 s. That is why the engine could change under you every week without breaking your bot.

def on_tick(self, market, portfolio):
    dd = 1 - portfolio.net_worth / self.peak
    if self.halted or dd >= self.max_dd:
        self.halted = True       # latched
        return self.flatten(portfolio)
    self.peak = max(self.peak, portfolio.net_worth)
    return self.signal(market, portfolio)

# and its test, at the threshold

What to notice
Armed at 4%, the switch trips early, flattens and stays off, so the loss stays near 4% while the unprotected bot sinks to almost 10%. A threshold above the worst drawdown is the same as no switch. Because the score is multiplied by (1 − 2 × drawdown), a 4% drawdown keeps 92% of a positive score and a 10% one keeps 80%.
Remember
The kill switch runs first in on_tick, is latched, and is tested at its threshold. In your bot: check it before any signal code, and write the test that it trips and stays tripped.

Part 2 · Git flow

  
How a company ships code: branches, pull requests, environments

  
Why this part exists
Part 1 made a change trustworthy on your laptop. A firm needs more: many people changing the same code, a record of who changed what, and a path to production that never crosses a trading session. Git flow is that path, branches, pull requests, tags and environments. Part 3 automates its gate with CI/CD and covers what to do when production still breaks.



  
Every branch has one job, every merge passes a gate, and production only ever runs a tag.

A pull request is the unit of review: a description of what and why, a linked ticket, tests, and
  required checks that branch protection enforces — lint, unit, integration, a coverage threshold — plus
  two approvals for anything that sends orders (the two-person rule). Merge it as a squash (one clean,
  revertable commit), a merge commit (full history) or a rebase (linear, rewritten). Commit messages follow
  conventional commits (feat(risk): …, fix: …, feat!: for a breaking change),
  which computes the semantic version — MAJOR.MINOR.PATCH — and writes the CHANGELOG.

    Three branching models, and when each fits
    
  
    
   
    Git flow
    develop + release branches, scheduled releases, several versions in support.
   Fits a bank with 400 developers, quarterly releases and a sign-off. Costs long-lived branches and merge pain.
    
   
    GitHub flow
    Short branches off main, PR, CI, merge, deploy. Fits a quant team of four shipping
   daily behind good tests. Costs main must always be deployable.
    
   
    Trunk-based
    Everyone commits to main at least daily; unfinished work hides behind feature flags;
   releases are flag flips. Fits teams with very strong CI. Costs discipline and flag hygiene.

    Part 3 · CI/CD and operations
    
  
    CI is a gate, CD ships what passes, and operations is what you do when it still breaks
    
  
    Why this part exists
    Part 2 drew the road from a branch to production; CI/CD is the machine that enforces it on every push, so nobody has to remember. Even then, live systems fail, usually partially, and the score that ranks you is risk-adjusted. This part covers the pipeline, the run-book and the score. The synthesis then puts all nine weeks on one map.
    


  
    
   
    
    
    # .github/workflows/ci.yml
on: [push, pull_request]          # every push, every PR
jobs:
  test:
    runs-on: ubuntu-latest          # a clean box, not yours
    strategy:
      matrix: { python: ['3.11', '3.12'] }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: ${{ matrix.python }} }
      - run: pip install -r requirements.txt   # pinned ==
      - run: ruff check .                      # lint
      - run: pytest -q --cov=team --cov-fail-under=85
        env: { ARENA_TOKEN: ${{ secrets.ARENA_TOKEN }} }   # never in git
    
   
    
   
    
    
    Pin exact versions (==), isolate in a virtual environment,
    containerise the whole environment so “same code + same dependencies + same OS” means the same behaviour.
    Secrets come from the CI secret store and the runtime environment, never from the repository or the image.
    
    
    The course runs the same gate on you: the template repository’s CI runs the tests on every push, and the
    autograder and live_readiness.py grade from the recording of the block, not from what you say happened.
    
    
    Observability is what makes the next incident short: structured logs for what happened, metrics for what is
    happening now, a dashboard with four panes — positions, P&L, risk, connectivity — and a run-book
    written cold and used hot. After an incident, a blameless postmortem: timeline, root cause, the test that would
    have caught it.

    # exchange/scoring.py · score_equity
excess = r - RISK_FREE_PER_SNAPSHOT
ratio  = mean(excess) / max(vol, VOL_FLOOR)
ratio  = clamp(ratio, -10, +10)
score  = ratio * max(0, 1 - 2 * mdd)   # if ratio >= 0

    The class demo (score_demo.py): both curves return +12.68%. Steady scores
   +10.000 — at the cap. Jagged, with 19.2% drawdown, scores +0.091. Defend the process, not the P&L.
   This widget recomputes the same function on a 200-snapshot path; the exact digits depend on the path.
    
  
    

    What to notice
    Same return, very different scores: the steady curve hits the +10 cap with no drawdown, while the jagged one is divided by its volatility and then multiplied by (1 − 2 × drawdown), 0.62 at 19.2%. Idle cash scores about zero because only the return above the risk-free drift counts. The class demo gave +10.000 against +0.091.
    Remember
    The season score is return per unit of risk with a drawdown penalty: the steadiest book wins, and a big drawdown always hurts. In your bot: size positions so the curve stays smooth, and let the kill switch cap the drawdown.

    Part S · The synthesis
    
  
    Nine weeks, one system: follow one order from a byte to a grade
    
  
    Why this part exists
    Parts 1 to 3 finished the toolkit. This part steps back and shows the whole system at once: one order, from the byte that carried the price to the grade it earned, through every piece you built. Each station says which week built it, why it is built that way and what breaks without it. The interview bank that follows tests the same chain, question by question.
    

  
    You built this stack bottom-up, one week at a time. A live order crosses it in a different order —
