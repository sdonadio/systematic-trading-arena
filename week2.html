Concurrency & Async in Python

A live trading system does a dozen things at once on a single thread — and exactly one blocking call is enough to freeze all of them, mid-session, while the market moves.

  • Say precisely what concurrency is, how it differs from parallelism, and pick threads, asyncio or processes from the workload alone.
  • Trace a coroutine through the event loop: ready queue, await, suspension, resume.
  • Keep on_tick non-blocking — offload blocking work with run_in_executor and bound your queues so back-pressure works for you.

Part 1

1What is concurrency — and what is it not?

Concurrency is structure: many tasks in progress, interleaved. Parallelism is execution: many tasks running in the same instant. One chef juggling six pans is concurrent. Six chefs at six stoves are parallel. Python's asyncio gives you the first and never the second — and for a trading bot, the first is almost always what you actually needed.

I/O-bound: the CPU is idle, waiting

A socket read. A Yahoo poll. Waiting for an OrderAck. The process is parked doing nothing while bytes are in flight. Ninety-five percent of what your bot does all session is this — which is why interleaving wins: while one task waits, another runs, on the same core.

→ asyncio. Thousands of concurrent waits, one thread, no locks.

CPU-bound: the core is pinned

Fitting a model over 5 years of ticks. Sweeping 400 parameter combinations. Nobody is waiting on anything — the core is genuinely busy. Interleaving buys you nothing here, because there is no idle time to fill.

→ processes. Real cores, separate memory, no GIL.

Processes

Separate memory, real parallelism, sidesteps the GIL. Best for CPU-bound work. Costs: heavyweight to start, and you need IPC or shared files to move data. multiprocessing

Threads

Shared memory, pre-emptively scheduled by the OS. Fine for blocking I/O because the GIL is released during the wait. No speedup at all for CPU-bound Python. Costs: races and locks. threading

Async / asyncio

One thread, cooperative scheduling, thousands of tasks. Best for high-volume I/O. Cost: nothing may block the loop, ever. async/await

The GIL, in one paragraph

CPython holds a Global Interpreter Lock: only one thread executes Python bytecode at a time. Four threads crunching numbers therefore take as long as one thread doing all four jobs — the lock serialises them. But the GIL is released around blocking calls: a socket read, a disk read, an HTTP request. That is why threads still help for I/O, and why the arena's one remaining thread is the blocking yfinance poller.

# 4 threads, CPU-bound — NO speedup (the GIL serialises them)
from threading import Thread
def crunch(n):
    while n: n -= 1        # pure Python bytecode
ts = [Thread(target=crunch, args=(10**7,)) for _ in range(4)]
[t.start() for t in ts]; [t.join() for t in ts]

Coroutines: functions that can pause

An async def function is a coroutine. Calling it does not run it — you get a coroutine object. Only await (or the loop, via a Task) drives it, and every await is a point where it may hand control back so something else can run.

async def fetch_quote(symbol):        # a coroutine
    await asyncio.sleep(0.2)          # pause here; loop runs others
    return {'sym': symbol, 'px': 185.5}

q = fetch_quote('AAPL')  # NOT run — a coroutine object
q = await fetch_quote('AAPL')  # now it runs

await asyncio.gather(              # ~3s total, not 6s
    worker('feed', 3), worker('quote', 2), worker('order', 1))

AlgoArena is async all the way down

  • Every process is an asyncio program. Exchange, brokers, traders — all networking is async over WebSockets, no blocking calls on the loop.
  • on_tick is a loop callback. The engine reads the socket, decodes the message and calls your hook. Return fast.
  • gather, not threads. Concurrent tasks are coroutines the loop interleaves: feed, orders, housekeeping.
  • Catch ConnectionClosed. Sockets drop. Your bot must reconnect, not crash — this is graded.

The one thread we keep, and why

yfinance is blocking HTTP with no async API. Put it on the loop and every quote, order and fill in the process stops for the duration of the request. So the broker runs it on its own thread and hands prices to the async side through shared state.

# broker/broker.py — yfinance is blocking HTTP
import threading, yfinance as yf

def poll_yahoo(symbols, out):      # runs on its OWN thread
    while True:
        px = yf.download(symbols)  # BLOCKING — cannot be on the loop
        out.update(px)             # hand to the async side

threading.Thread(target=poll_yahoo, daemon=True).start()
# the async quoting logic reads 'out'; the loop never blocks

Part 3

3Why does this matter in trading?

Because a frozen loop is not a slow bot — it is a blind bot. While your coroutine sits inside time.sleep() or requests.get(), nothing reads the socket. Book updates queue up in the kernel, your view of the market goes stale, your resting orders get picked off at prices you would never have quoted, and the fills you do get land on decisions made a second ago. # WRONG — freezes EVERY task on the loop
async def on_tick(...):
    time.sleep(1.5)                 # blocks all tasks
    r = requests.get(url)         # blocking HTTP

# RIGHT — yield, or offload to a thread
async def on_tick(...):
    await asyncio.sleep(1.5)        # non-blocking
    loop = asyncio.get_running_loop()
    r = await loop.run_in_executor(None, requests.get, url)

Races: why async is safer, and where it still is not

On one loop, one task runs at a time and only yields at an await — so a plain read-modify-write between awaits is atomic, and most of the classic thread-race bugs simply cannot happen. What can still happen: state changing across an await. If you read a position, await a send, then write the position back, something else ran in between and you have just clobbered it.

  • asyncio.Lock — guard a critical section that spans awaits.
  • threading.Lock — required for genuinely shared data across real threads.
  • Better: do not share mutable state at all. Hand data between tasks through an asyncio.Queue.

This week's code: offload, do not block

import asyncio
from arena import Trader, Signal

class MyBot(Trader):
    async def on_tick(self, market, portfolio):
        ask = market.best_ask('AAPL')
        if ask is None:
            return None
        loop = asyncio.get_running_loop()
        # offload a blocking signal calc — never block the loop
        score = await loop.run_in_executor(None, heavy_calc, ask)
        if score > 0:
            return Signal('AAPL', 'buy', 1, ask)
        return None

Verify it by watching fills keep arriving while heavy_calc runs. If they stop, you did not offload — you moved the freeze.

Part 4

4Five ways this goes wrong

Four of these five will cost you fills in a live session. Open them.

time.sleep() or requests.get() inside a coroutine

The canonical mistake, and it is silent: no exception, no warning, just a bot that is inexplicably worse than it was in the backtest. Any blocking call inside async def stops the entire loop — feed, orders, heartbeat, everything.

It hides in innocent places: a pandas.read_csv on a big file, a print() to a slow terminal, a synchronous yfinance call you added "just to check something".

Fix: await asyncio.sleep() for delays, an async HTTP client for requests, and await loop.run_in_executor(None, fn, *args) for anything blocking you cannot replace.

Forgetting to await, and getting a coroutine object

result = self.compute_signal() where compute_signal is async def gives you a coroutine object, not a number. It is truthy, so if result: is always true, and Python only mutters "RuntimeWarning: coroutine was never awaited" if you happen to be watching stderr.

The mirror-image bug: asyncio.create_task(coro) and then dropping the reference. The task can be garbage-collected mid-flight and its exception disappears with it.

Fix: await it, or keep the task in a set. Run with PYTHONASYNCIODEBUG=1 during development and treat the warnings as errors.

An unbounded queue as a memory leak with extra steps

asyncio.Queue() with no maxsize never applies back-pressure. A fast feed and a slow strategy means the queue grows until the process dies — and long before it dies, your strategy is acting on ticks that are ten seconds old.

Stale is worse than missing. A book snapshot from 8 seconds ago is not "some information"; it is actively wrong information you are about to send an order against.

Fix: bound it (maxsize=100) so put() waits, or coalesce — keep only the newest snapshot per symbol and throw the rest away.

Reaching for threads to make CPU-bound work faster

Four threads fitting four models is exactly as slow as one thread fitting four models, because the GIL lets only one of them execute bytecode at a time. You paid for locks, races and debugging and got nothing.

The exception that confuses everyone: NumPy, pandas and scikit-learn release the GIL inside their C loops, so threads sometimes do help. That is a property of the library, not of your code — do not plan around it.

Fix: CPU-bound → multiprocessing or ProcessPoolExecutor. Threads are for blocking I/O with no async API.

Letting ConnectionClosed kill the bot

Networks blink. Wi-Fi hiccups, the exchange restarts, a laptop lid closes. An uncaught websockets.exceptions.ConnectionClosed ends your session and your score stops accumulating at whatever it was — often with a position still open.

Reconnecting badly is its own trap: a tight retry loop hammers a recovering server, and resuming without re-syncing means your book is a fiction.

Fix: catch it, reconnect with exponential backoff, re-handshake, and request a fresh snapshot rather than assuming continuity. Then flatten or re-assert your risk state.
