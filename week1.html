Part 1

1What is object-oriented programming?

Look at a market and you see nouns. An order with a side and a price. An order book that holds orders and matches them. A portfolio that owns cash and positions. A strategy that turns prices into intentions. Object-oriented programming is simply the decision to make each of those nouns a thing in your program that keeps its own state and knows how to behave.

The alternative — a pile of functions passing dictionaries around — works fine for a hundred lines and collapses at ten thousand. By Week 9 your bot will hold a portfolio, a risk stack, a signal model, a reconnecting socket client and a scoring hook. If those are five objects with clear contracts you can test them separately and swap one without touching the rest. If they are one 900-line main(), every change is a gamble.

There are four reasons the arena is built this way, and they are the four reasons the course starts here:

  • Model reality. Code that mirrors the domain is code you can reason about — and argue about with a colleague.
  • Manage complexity. A trader calls on_tick(); it never touches sockets, auth or matching.
  • Enable extension. A new security, shock or strategy is a new subclass or plugin, not a rewrite.
  • Make it testable. Small objects with clear contracts are unit-testable in isolation; the arena ships ~1,280 tests around them.

The vocabulary, once

class Order:
    exchange_fee = 0.001          # class attribute (shared)

    def __init__(self, symbol, side, qty, price):
        self.symbol = symbol      # instance attributes
        self.side   = side        # (per-object state)
        self.qty    = qty
        self.price  = price

    def notional(self):           # a method (behaviour)
        return self.qty * self.price

o = Order('AAPL', 'buy', 5, 185.50)  # an instance
o.notional()   # -> 927.5

A class is the blueprint; an object is one instance of it. __init__ sets up state, self is this particular object, and a method is behaviour that can see that state.

Encapsulation — a stable interface over changeable internals

Bundle state and behaviour together, then hide the internals. Python has no hard access control: name is public API, _name means "internal, hands off", and __name is name-mangled. A @property lets you expose a computed value as if it were an attribute — so net_worth can start as a stored float and become a live mark-to-market calculation without breaking one caller.

In the arena: Portfolio.net_worth is a property. Marking positions changed three times during development; no bot ever noticed.
class Portfolio:
    def __init__(self, cash):
        self.cash = cash          # public
        self._positions = {}      # _protected (convention)
        self.__ledger = []        # __private (name-mangled)

    @property
    def net_worth(self):          # computed, read-only
        return self.cash + self._mark_positions()

p.net_worth        # attribute access, runs the method
p.net_worth = 10   # AttributeError — no setter

Abstraction — say what it does, not how

An abstraction is a promise about behaviour with the mechanism deleted. Your bot's promise is one line: given the market and my portfolio, return a Signal or None. Underneath that line sit a WebSocket client, a token handshake, JSON serialisation, reconnection with backoff, a matching engine and a fee model — none of which you import, mention or can break.

In the arena: the arena package is the only thing a student imports. Everything in exchange/, shared/ and trader/ is behind it.
# what you write — the whole surface area
from arena import Trader, Signal

class MyBot(Trader):
    def on_tick(self, market, portfolio):
        ask = market.best_ask('AAPL')
        return Signal('AAPL', 'buy', 1, ask) if ask else None

MyBot().run()      # sockets, auth, retries: not your problem

Inheritance — genuine specialisation, and nothing else

A subclass reuses a base class and specialises it; super() calls back into the parent, and Python resolves which method runs via the MRO. Inheritance is the right tool when the sentence "a Momentum IS-A Strategy" is true. It is the wrong tool when you only wanted to borrow some code — that is what composition is for, and it is the single most common design error we will see in your Week-1 diagrams.

Rule of thumb: reach for composition first. Use inheritance only when a caller holding the base type could be handed the subclass and never notice.
class Strategy:
    def __init__(self, name):
        self.name = name
    def signal(self, prices): ...      # base behaviour

class Momentum(Strategy):              # Momentum IS-A Strategy
    def __init__(self, name, lookback):
        super().__init__(name)         # call parent __init__
        self.lookback = lookback
    def signal(self, prices):          # specialise
        return prices[-1] - prices[-self.lookback]

Polymorphism — one call site, many behaviours

The engine holds a list of bots. It calls on_tick() on each of them and has no idea which class it is talking to. That is polymorphism: one interface, many implementations, chosen at runtime. Python does not even require a shared base type — if it has on_tick(), it is a trader. Duck typing is powerful and it is a contract you must honour by hand, which is exactly why the arena pins it down with an ABC.

Why you care: this is what lets the season add a new house bot, a new shock, or a new security without the engine changing a line. Open for extension, closed for modification.
def run_all(bots, market, portfolio):
    for bot in bots:                    # each bot is a different class...
        sig = bot.on_tick(market, portfolio)   # ...same call, different logic
        if sig: submit(sig)

run_all([Momentum(...), MeanReversion(...), MLBot(...)], mkt, pf)

2How does UML work? Build the diagram yourself

A UML class box is three compartments: name, attributes, methods. + is public, - is private, # is protected, and a dashed border marks an abstract class. The arrows are where the design actually lives — they say how objects know about, use, and own one another.

The five links you need this week

GlyphNameMeans
▷——GeneralizationIS-A. Momentum is a Strategy.
◆——CompositionOWNS, shared fate. A Bot owns its Portfolio.
◇——AggregationHAS-A, separate lifetime. A venue has bots that outlive it.
——AssociationUses. A Trader uses MarketData.
- - ›DependencyTransient use. A method returns a Signal.

Multiplicity goes on the ends: 1, 0..1, *. An OrderBook holds * Orders.

Why bother drawing it

  • It aligns humans. A picture settles an argument that three paragraphs of prose cannot.
  • It aligns your AI. Paste the diagram into Claude and the generated code lands in the right shape; describe it in prose and it invents its own.
  • It is cheap to be wrong. Moving an arrow costs a minute. Moving an inheritance relationship out of 2,000 lines costs a week.
  • It is a living artifact. You will extend this same diagram every week: async pipeline (W2), wire messages (W3), backtester (W4).

The contract underneath it all: an ABC

An abstract base class turns "we agreed on the shape" into something Python enforces. arena.Trader has exactly one @abstractmethod. You cannot instantiate it until you implement that method — which is why a Level-1 bot cannot silently do nothing wrong.

from abc import ABC, abstractmethod

class Trader(ABC):
    @abstractmethod
    def on_tick(self, market, portfolio):
        ...            # every subclass MUST implement this

class MyBot(Trader):
    def on_tick(self, market, portfolio):
        return Signal('AAPL', 'buy', 5, market.best_ask('AAPL'))

Trader()      # TypeError: can't instantiate abstract class
MyBot()       # OK — the contract is satisfied

Value objects: dataclasses, and where pydantic takes over

A @dataclass writes __init__, __repr__ and __eq__ for you, and the type hints double as the schema. Use them for data-holding objects you create inside your own process. The moment an object goes on the wire, it needs validation as well as structure — that is why shared/messages.py uses pydantic v2 models instead (Week 3).

from dataclasses import dataclass

@dataclass
class Trade:
    symbol: str
    price: float
    quantity: int
    aggressor: str

t = Trade('AAPL', 185.5, 5, 'buy')   # __init__ free
print(t)   # Trade(symbol='AAPL', price=185.5, ...)
SOLID, one line each: Single responsibility · Open/closed (this is the plugin registry) · Liskov substitution · Interface segregation · Dependency inversion.

3Why does this matter in trading?

Because the interface is the thing you keep and the strategy is the thing you throw away. Over nine weeks you will write and delete a dozen signals. If every one of them is a Strategy behind the same signal() call, swapping them is a one-line change and you can run them side by side on the same price path. If each one is welded into your socket loop, you get one shot per week.

Part 4

4Five ways this goes wrong

Every one of these has been marked down in a real Week-1 deliverable. Open them.

Using inheritance where you meant composition

The classic: class Bot(Portfolio), because the bot needs cash and positions and inheriting them is fewer keystrokes. Now bot.apply_fill() is public API, your bot is a portfolio to every caller, and the day you want two portfolios (live and shadow) the design has no room for the second one.

Read the arrow out loud. "A Bot IS-A Portfolio" is false. "A Bot HAS-A Portfolio" is true.

Fix: self.portfolio = Portfolio(cash) — composition, one line, and now swappable and mockable in tests.

A god object called Bot

One class that polls the feed, computes the signal, sizes the position, checks risk, formats the order, manages the socket and prints the dashboard. It always starts innocently as 60 lines.

The symptom is that you cannot unit-test the signal without a network connection, so you stop testing the signal. By Week 5 you cannot profile it either, because everything is one function.

Fix: single responsibility. Signal generation, RiskManager sizing, and the transport are three objects. The arena SDK already owns the third one for you.

Believing _private is enforced

Python will happily let anyone touch bot._positions. The underscore is a message to humans, not a lock — and __name is only name-mangled, not sealed.

The real failure is the inverse: exposing mutable internals by accident. Returning self._positions from a "getter" hands the caller your live dictionary, and a bug three files away silently rewrites your book.

Fix: return copies or read-only views, and put computed state behind @property so you can change the implementation later.

A UML diagram with arrows but no meaning

Ten boxes joined by ten identical plain lines. It looks like a design and communicates nothing: the marker is what distinguishes "owns" from "inherits from" from "happens to call once".

Second version of the same mistake: arrows that point the wrong way. Generalization points from the subclass up to the base. Composition's filled diamond sits at the owner end.

Fix: every link gets a glyph and, where it helps, a multiplicity and a verb — Bot ◆— 1 Portfolio, OrderBook ◆— * Order.

Letting the AI own the design

"Write me a trading bot" produces a plausible 200-line file with a class hierarchy you did not choose and cannot defend in a design review — which is a graded part of this course.

Claude is excellent at the inverse task: give it your diagram and ask it to find the relationship that is wrong, generate the dataclass, or explain what arena.Trader's contract obliges you to implement.

Fix: you draw the boxes and arrows; the AI fills in bodies. If you cannot explain why a class exists, delete it.
