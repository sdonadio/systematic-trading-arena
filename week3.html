Socket Streaming & Protocols

TCP hands you bytes, not messages. A trading system is only as reliable as the contract that turns one into the other — and that contract is a thing you design, not a thing you find.

Part 1

1What is a protocol? Start with what TCP does not give you

Week 2 gave you one process doing many things at once. Now there are many processes — the exchange, every broker, every trader, often on different machines — and the only thing they can do is send each other bytes. A stream of bytes means nothing until both sides agree on which messages exist, what fields they carry, and what a valid reply looks like. That agreement is the protocol, and it is the most load-bearing design decision in the system.

Four layers you actually care about

  • Link / physical — wires, Wi-Fi, MAC addresses. Not your problem.
  • Internet (IP) — routes packets between hosts. Best-effort, no guarantees.
  • Transport (TCP/UDP) — process-to-process delivery via ports. Where reliability is, or is not.
  • Application — HTTP, WebSocket, your protocol. What the messages mean.

An address is host:port. The arena exchange is localhost:8765 — an IP plus a TCP port a process is listening on. Your JSON rides inside a TCP segment, inside an IP packet, inside a frame; each layer wraps the one above.

TCP vs UDP, and why we chose TCP

We need every order and every fill, exactly once, in order: correctness beats microseconds in this course, so WebSocket over TCP is the right default. Real venues also multicast market data over UDP, where a lost packet is better than a late one — but they pay for that with sequence numbers and gap-fill machinery you do not want in week three.

The catch: TCP is a stream. Two send()s can arrive as one recv(), and one send() can arrive split across three. There is no "message" until you make one.

Request / response

Client asks, server answers, done. HTTP and REST. Simple — but the client has to keep asking to learn what changed, and it still misses everything that happened between two polls. Useless for a book that moves every 50 ms.

Streaming

One connection stays open and the server pushes updates as they happen. No re-asking, no per-message HTTP header tax, no gap between polls. This is how you receive market data.

Publish / subscribe

Publishers emit to topics; subscribers get what they asked for. Decouples senders from receivers, so one book update fans out to every trader without the exchange knowing who they are.

The arena blends all three over one persistent WebSocket: streamed pushes (BookSnapshot, TradeExecution) and request/response pairs (PlaceOrder → OrderAck) on the same connection, in both directions, simultaneously.
Part 2

2How does it work? The handshake, then the conversation

A WebSocket is born as an HTTP request and then stops being one. The client asks to upgrade; the server answers 101 Switching Protocols; from that moment the same TCP connection is full-duplex and framed, and every await ws.recv() returns exactly one whole message. Why not HTTP polling?

  • Polling sends a fresh request every N ms: new headers, often a new connection, and you still miss everything between two polls.
  • Long-polling / SSE help, but SSE is half-duplex — server to client only. A trader has to send orders too.
  • WebSocket upgrades once, then both sides push frames whenever they like with a few bytes of header.

And crucially: framed. The protocol delimits messages for you, so the entire first widget on this page becomes somebody else's problem.

Keeping a long-lived connection healthy

  • Back-pressure. Bound your queues, coalesce stale book updates, and let asyncio await the drain. (Week 2's widget, in production.)
  • Heartbeats. A dead TCP connection can look alive for minutes. Periodic ping/pong finds a silent peer fast and stops NATs closing an idle pipe.
  • Reconnection. Exponential backoff, re-handshake, then request a fresh snapshot — never assume continuity.
  • Idempotency. A retried order must not double-execute. Client-side IDs let the server dedupe a repeat.

Text or binary?

JSON (text). Readable, debuggable, universal — you can watch a session in a terminal and understand it. Slightly larger on the wire. The arena's choice: clarity over bytes for a teaching platform, and 8765 is not a colo cross-connect.

protobuf / msgpack (binary). Compact and fast, but opaque without the schema. What real venues use for market data. Rule: stay text until profiling proves you need binary — then you will need the schema discipline in Part 3 even more, not less.

Part 3

3Why does this matter in trading?

Because a malformed order is not a nuisance — it is either a rejected trade or, far worse, an accepted one that corrupts the book. The arena has one sacred rule in both directions: never send a raw dict, and never pull fields out of raw JSON. Every message is a pydantic v2 model in shared/messages.py; the class is the contract, and a bad message dies at the boundary instead of three layers deep inside matching.

The cost of a raw dict

  • msg['quatity'] — a typo is a KeyError at runtime, in production, mid-session.
  • No autocomplete and no guarantees: you cannot know what fields exist without reading every producer.
  • Silent drift — change a field on one side and the other breaks somewhere far away, with no error at the boundary.

The value of a typed model

  • order.quantity — the IDE completes it, the type checker verifies it, the validator guarantees it is an int.
  • Errors surface at parse time with a precise ValidationError, naming the field.
  • The model is the documentation: the class definition is the authoritative spec of the message.

from typing import Literal

    team_id: str
    symbol: str

In the arena this is one function call: parse_message(json.loads(raw)) looks at the type discriminator, picks the right model out of a union, and calls model_validate. Unknown type → KeyError; bad shape → ValidationError. Both are caught at the edge and logged; neither kills the connection.

Discriminated unions: many message types, one channel

# shared/messages.py — keyed on the 'type' field
AnyClientMessage   = Union[Handshake, PlaceOrder,
                           CancelOrder, ...]      # client → exchange
AnyExchangeMessage = Union[OrderAck, BookSnapshot,
                           TradeExecution,
                           PortfolioUpdate,
                           SessionEvent, ...]     # exchange → client

def parse_message(raw: dict) -> BaseModel:
    msg_type = raw.get('type')          # the discriminator
    model_cls = _TYPE_MAP.get(msg_type) # unknown -> KeyError
    return model_cls.model_validate(raw)  # bad -> ValidationError

One tag field selects the model, so dispatch is O(1) and unambiguous — the parser never has to guess a shape from its keys. The direction is encoded in the union name: AnyClientMessage is what you send, AnyExchangeMessage is what you receive.

Three failure modes, three answers. Malformed (missing field, bad enum): reject with a clear error, never let it reach business logic. Unknown type (a newer peer, a bug): log and skip — do not kill a connection over one frame. Not even JSON: catch the decode error, and consider closing if it repeats.

Part 4

  
4Five ways this goes wrong

  
The first one has cost every cohort at least one session. Open them.


  
Assuming one recv() equals one message
    

      
Over a raw TCP socket, json.loads(sock.recv(4096)) works perfectly on your laptop with
      one small message and fails the moment the market gets busy — because two sends coalesced into one
      read, or one send arrived in three pieces.

      
The failure is intermittent and load-dependent, which is the worst kind. It shows up in the live
      session and not in your test.

      
Fix: frame explicitly (length prefix or delimiter) and keep a buffer across reads — or
      use WebSockets, which frame for you, which is exactly why the arena does.

    


  
Sending raw dicts and hand-parsing raw JSON
    

      
await ws.send(json.dumps({'type': 'place_order', 'quatity': 5})) is accepted by
      json.dumps, accepted by the socket, and rejected by the exchange — or worse, silently
      interpreted with a missing field defaulting to something you did not intend.

      
On the receive side, raw['price'] against a message that does not have a price is a
      KeyError deep inside your strategy, mid-session, with a position open.

      
Fix: model.model_dump_json() to send;
      parse_message(json.loads(raw)) to receive. No exceptions, ever. This is graded.

    


  
Letting one bad frame kill the connection
    

      
An unknown type, a truncated frame, or a field the newer exchange added and your
      parser was configured to forbid — and an unhandled exception propagates out of your read loop and ends
      the session.

      
Being strict on the send path is discipline. Being strict on the
      receive path is fragility: you cannot control what a peer sends you.

      
Fix: try/except (KeyError, ValidationError) around the parse; log and
      continue. Ignore unknown fields inbound. Only close the connection if the garbage repeats.

    


  
A "small" breaking change to a live protocol
    

      
Renaming quantity to qty, tightening a type, or making an optional field
      required. Each is a one-line diff and each instantly breaks every peer that has not redeployed —
      including three teams whose bots are running from last week's branch.

      
The subtler version: keeping the field name but changing its meaning — price
      from dollars to cents, quantity from shares to lots. Nothing errors. Everything is wrong.

      
Fix: add, never change. New fields are optional with defaults; if you truly must
      replace one, carry both for a version and use an alias.

    


  
No heartbeat, no backoff, no resync
    

      
A half-open TCP connection looks perfectly alive from your side: no error, no data, forever. Your
      bot sits happily reading nothing while the session runs without it.

      
Then the reconnect makes it worse — a tight retry loop hammers a recovering exchange, and resuming
      without requesting a fresh snapshot means you are trading against a book you remember rather than the
      one that exists.

      
Fix: ping/pong with a timeout, exponential backoff on reconnect, re-handshake, then
      request a fresh BookSnapshot before sending a single order.
